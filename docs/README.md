# Just-in-time rules: deliver rules per action, never keep them resident

In one sentence: rules stay out of the context by default; a program decides which rule applies to the current action and puts the rule text in front of the model before it generates. This replaces the habit of writing rules up front into always-loaded files such as CLAUDE.md or AGENTS.md.

Reading order: this document → [harness-hooks.md](harness-hooks.md) (how each harness supports delivery) → [design/](design/README.md) (design decisions, for people) → [runbook/](runbook/README.md) (the implementation manual given to the coding agent).

## Goal

The context should hold only the rules the current action needs. Rules should not have to be written into resident files in advance, and should not depend on the model remembering to look them up. A user should never have to say the same thing twice.

## Decisions and principles

1. **Delivery is the only way a rule enters the context.** The rule library is the single source; each rule is a trigger condition plus one or two sentences of rule text. CLAUDE.md and AGENTS.md keep only what has no definable trigger and must always apply.
   Principle: a rule whose trigger can be defined should not sit in the context. Resident rules take up space and get diluted late in long sessions.

2. **A program decides when to deliver, not the model.**
   Principle: the model cannot remember to look up a rule it cannot see. Skills leave "should I use this" to the model, and every skill description has to stay resident.

3. **Trigger on two kinds of events: user requests and tool calls.**
   Principle: a rule must arrive before the model generates. The moment a rule is needed may be when the user makes a request, or at a specific action in the middle of a task.

4. **The judge matches the current event directly against each rule's trigger; there is no intermediate intent layer.**
   Principle: a program cannot see intent, and the same Edit can serve entirely different intents; intent is only a proxy anyway. The real difficulty is whether the trigger is written clearly enough, and that can be iterated on by replaying logs.

5. **The judge prefers over-triggering to missing.** The implementation is replaceable (System One, a small LLM, embeddings); choose by latency, cost, and whether probabilities are calibrated.
   Principle: a missed trigger means the rule does not exist; an extra trigger only costs a few lines of context.

6. **Inject what can be delivered before generation; block (deny) when the content is already in the tool arguments, and attach the rule as the reason so the model rewrites.**
   Principle: the rule must precede generation. When writing a document or a commit message, the content is already generated by the time the tool is called.

7. **Redeliver by context distance, not once per session.**
   Principle: delivered rules are also diluted as the context grows.

8. **The rule library grows from user corrections.** Every time a user repeats something, turn it into a rule with a trigger.
   Principle: nobody should have to say the same thing twice.

9. **Across harnesses, the lowest common denominator is "block and return the reason to the model"; "inject context while allowing" is an enhancement.**
   Principle: every harness supports blocking; support for injection is incomplete. See [harness-hooks.md](harness-hooks.md).

## Findings from practice

- **The problem is real.** The author's global CLAUDE.md already says "write only decisions and the principles that govern them", yet when writing design documents it still has to be repeated, otherwise the AI produces enumerations like "A, B, C, D are out of scope". Evidence: usage (the author's own experience).
- **Mainstream harnesses support a hook before tool calls.** Claude Code, Codex, TRAE, DeepSeek Harness, and Cline all support injecting context while allowing a call. Evidence: implementation (official docs, source code, local binaries).
- **An external judge plus a one-line injection reduces wrong loads.** TypeSafe's skill_suggestion cookbook reports the rate of loading the wrong skill dropping from 16.8% to 7.3%. Evidence: vendor-reported result, not reproduced; its rule descriptions are still resident, and it triggers on every user turn.
- **Blocking must apply to every violation, and this does not trap the model in a loop.** The first design blocked only once within a distance window, and during acceptance a violating write on Claude Code got through. After switching to blocking every violation: when the rule conflicted with the user's request, both Claude Code and Codex stopped and explained the conflict to the user instead of working around it; when the rule could be satisfied, Claude Code fixed the content and rewrote (that case did not occur for Codex in this run). Codex also creates files with shell commands (`printf ... >> notes.md`), which a watch on file-writing tools alone would miss. Evidence: usage and results (measured, 1–2 runs each, see [design/verification.md](design/verification.md)).
- **Rule violations over long trajectories have been measured.** OctoBench and the goal-drift line of papers show agents violating system prompts and repository conventions during multi-step tasks, and grading only the final result misses these violations. Evidence: results (public benchmarks).

## Hypotheses to test and evaluation

- **Core hypothesis**: with rules delivered only just in time, compliance is no lower than with rules resident in CLAUDE.md, while resident context shrinks noticeably. Control: rules resident. Treatment: delivery only.
- The judge's recall is high enough. Evaluated offline: sample events from the logs and label by hand which rules should fire; this is independent of context length.
- After a block, the model rewrites according to the rule, at an acceptable cost.
- The effect of delivery can only be measured in long sessions. Evaluate in this order:
  1. Replay real sessions: cut the context just before a violation and replay several times under each arm;
  2. Run [OctoBench](https://arxiv.org/pdf/2601.10343) for externally comparable numbers;
  3. Keep counting how often users have to repeat themselves.

## Positioning

This is a harness-level feature, not a standalone product; once the official harnesses ship an equivalent mechanism, it is superseded.
