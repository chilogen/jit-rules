# Spec: packs, profiles, lock file, registry, active unit set

Go types are in [contracts.md](contracts.md).

**Overall principle**: the AI may edit files freely, but only content that has been tested and confirmed, and not changed since, reaches the AI. "Not changed since" is always decided by hash: one's own units by file hash, packs by the hash of the whole pack.

## Packs

Directory structure:

```
<pack root>/
├── pack.yaml
├── README.md        # optional, for people
├── LICENSE          # optional
└── units/*.md
```

`pack.yaml` (parsed with `KnownFields(true)`):

```yaml
name: team-writing      # required, ^[a-z0-9][a-z0-9-]{0,39}$
version: 1.2.0          # required, any string, for display only
description: 团队写作规范  # required
```

- `pack.Validate(dir)`: apart from the `.git` directory, a pack may contain only `pack.yaml`, `README.md`, `LICENSE`, and `units/*.md`; any other file or directory (especially executables) is an error that lists them. Reason: packs are installed from the community, so they may contain only data, never code.
- Every file in `units/` must parse and pass `unit.Validate` (no errors); otherwise the whole pack is rejected.
- The name `core` is reserved for the built-in pack.

### Pack hash (`pack.Hash`)

For `pack.yaml` and `units/*.md`, in lexical order of relative path (`/`-separated), concatenate one line `<relative path>\t<sha256 hex of the file's bytes>\n` each; take the sha256 of the concatenation, written as `"sha256:" + hex`.

### Three kinds of source

| source | Used for | Where the content lives | Lock record needed |
|---|---|---|---|
| The literal `builtin` | The built-in core pack | Embedded in the binary (`pack.Builtin()`), never on disk | No. Its content is pinned by the jitr version; upgrading jitr upgrades core |
| A local directory | Developing your own pack | The original directory, not copied | Yes: `hash` |
| Anything else (treated as a git URL, including `file://`) | Community packs | `{data}/packs/<pack name>/<commit>/` | Yes: `commit`, `hash` |

When the source given to `jitr pack add` is an existing directory (a relative path is first made absolute against cwd), it is a local source; otherwise, a source containing `://` or starting with `git@` is a git URL; anything else is a user input error: "找不到目录 <source>" ("directory <source> not found").

### Fetching a git source (`pack.Fetch(source, ref)`)

1. If no git executable is found, the error is "需要安装 git 才能从 git 仓库安装包" ("git is required to install a pack from a git repository").
2. Create a temporary directory under `{data}/packs/.tmp/` and `git clone <source> <temp dir>` (a full clone without `--depth`; rule repositories are small, and only a full clone supports branches, tags, and commits alike).
3. When ref is non-empty, try `git rev-parse --verify --quiet origin/<ref>^{commit}` and then `git rev-parse --verify --quiet <ref>^{commit}`; the first that succeeds is the commit to use; if both fail, the error is "找不到 ref <ref>" ("ref <ref> not found"). Then `git checkout --detach <commit>`. When ref is empty, use `git rev-parse HEAD`.
4. Delete `.git` in the temporary directory, read `pack.yaml` for the pack name, and rename the temporary directory to `{data}/packs/<pack name>/<commit>/`; if the target exists, delete it first (the directory's content is determined by the commit alone, so fetching again is always safe).
5. If any step fails, delete the temporary directory.

Reason: branches move, so both the directory and the lock are keyed by commit; when `pack update` fetches again, a branch naturally gets its latest commit. At hook time only the commit directory recorded in the lock is read, and the network is never used.

## Profiles

Directory structure:

```
<profile dir>/
├── profile.yaml
├── jitr.lock        # written by jitr, readable by people, not to be edited by hand
└── units/*.md       # the user's own units
```

`profile.yaml` (parsed with `KnownFields(true)`):

```yaml
name: me                     # required, ^[a-z0-9][a-z0-9-]{0,39}$, may not be core
description: 我的规则          # optional
packs:                       # order matters: earlier packs rank higher
  - name: core
    source: builtin
  - name: team-writing
    source: https://github.com/x/jitr-team-writing.git
    ref: v1.2.0
    include: ["writing.*"]   # optional, globs over short ids, default ["*"]
    exclude: []              # optional
disable: [team-writing/writing.legacy]   # optional, list of global ids
settings: {}                 # optional, see below
```

Content generated by `profile.Init(dir, name)`:

```yaml
name: <name>
packs:
  - name: core
    source: builtin
settings: {}
```

It also creates an empty `units/` directory and an empty jitr.lock (`version: 1`, with empty units and packs). When `dir` is not inside any git repository (no `.git` under `paths.ProjectRoot(dir)`), run `git init` (skipped if git is missing).

### settings

Defaults come from the embedded `assets/defaults.yaml` (contents in runbook/assets/defaults.yaml). Merging: treat the defaults and each profile's `settings` as `map[string]any` trees and deep-merge them in the order of step 7 of Resolve (when both sides are maps, merge recursively; otherwise the latter overrides), then marshal the result to YAML and unmarshal it into `Settings`.

If settings contains a key ending in `api_key` that is not `api_key_env`, loading that profile fails with "不要在 profile 里写 API key，请改用 api_key_env 指定环境变量名" ("do not write API keys in a profile; name an environment variable with api_key_env instead").

### jitr.lock

`SaveLock` rewrites the whole file every time: the first line is the comment `# 由 jitr 生成。记录哪些单元和包已经生效。不要手动修改。` ("Generated by jitr. Records which units and packs are in effect. Do not edit by hand."), followed by the YAML of `Lock`.

```yaml
# 由 jitr 生成。记录哪些单元和包已经生效。不要手动修改。
version: 1
units:
  me/git.commit-zh:
    hash: sha256:3f2a...
    enabled_at: 2026-11-02T10:00:00Z
    tests: {passed: 4, failed: 0, skipped: 0}
packs:
  team-writing:
    source: https://github.com/x/jitr-team-writing.git
    ref: v1.2.0
    commit: 9c1e...
    hash: sha256:77ab...
    added_at: 2026-11-02T09:00:00Z
```

**What takes effect**:
- A profile's own unit: its id is in `units` and its `hash` equals the file's current hash.
- A builtin pack: takes effect whenever it is listed in `packs` of profile.yaml.
- Local and git packs: listed in `packs` of profile.yaml, with a record of the same name in the lock's `packs` whose `hash` equals the pack's current hash (git packs are hashed under `pack.GitDir(name, commit)`). When the directory is missing or the hash differs, the pack does not take effect and `Resolved.Errors` gets the entry "包 <name> 已被修改或缺失，运行 jitr pack update <name>" ("pack <name> was modified or is missing; run jitr pack update <name>").

### Modifying profile.yaml

`AddPack`, `RemovePack`, `SetPackRef`, `AddDisable`, and `RemoveDisable` are all implemented the same way: parse the file into a `yaml.Node` with yaml.v3, find the node to change, change only that node (append or delete a sequence element, or change a scalar), and write the whole tree back. Decoding the file into a struct, modifying the struct, and merging it back into the nodes is **not allowed**: that approach cannot delete anything (the previous implementation's `pack remove` silently failed because of it).

- When the `packs` or `disable` key is missing, `AddPack` and `AddDisable` create it; when `RemovePack` and `RemoveDisable` delete the last element, an empty sequence `[]` is kept.
- `AddPack` fails on a pack with the same name; `RemovePack` and `SetPackRef` fail when the pack is not found; `AddDisable` does nothing when the id already exists; `RemoveDisable` does nothing when it is not found.

### Writing files

Every write of profile.yaml, jitr.lock, or registry.yaml uses `fileutil.WriteAtomic`. Changes initiated by CLI commands then call `profile.Commit(dir, "jitr: <description of the operation>")`: when the profile directory is itself a git repository (`<dir>/.git` exists), run `git add -A` and `git commit -m <description>`; failure (for example no git user configured, or nothing to commit) returns a warning that the CLI prints, not an error.

## Registry `{config}/registry.yaml`

```yaml
version: 1
profiles:
  - path: /home/u/.jitr             # the user's global profile
  - path: /home/u/work/repo/.jitr
```

The registry stores explicitly registered, trusted profile paths. Each path is absolute and must name a `.jitr` directory; loading or saving an entry with another directory name fails. Scope is derived from the path, not stored: registry v1 has no `scope` field, and unknown YAML fields are rejected. `registry.Save` rewrites the whole file.

**Profiles that apply to cwd** (in the hook, cwd is the event's session cwd; the paths an event touches play no part): the registered `~/.jitr` profile applies everywhere (`~` is the user's home directory, independent of `JITR_HOME`). Every other registered `.jitr` applies to its parent directory and that directory's descendants. `registry.IsGlobal` identifies the global profile; `registry.Scope` returns the parent directory of a profile path. Unregistered `.jitr` directories are not loaded automatically.

**Ranking** (the order returned by `registry.Applicable`, highest first): applicable project profiles come first, from the nearest ancestor outward (descending scope path length); the global profile comes last. Existing same-topic arbitration therefore keeps the nearest applicable rule.

## Active unit set (`profile.Resolve(cwd)`)

1. Read the registry and take `Applicable(entries, cwd)`; the i-th profile has rank i.
2. **Collect units within each profile**, each tagged with the rank pair `(profile rank, source rank)`:
   - Source rank 0: the profile's own `units/*.md`. Parse every file: a parse or validation error → status `invalid` (and if it is in the lock with the same hash, also add an entry to Errors); absent from the lock → `draft`; different hash → `modified`; otherwise it is a candidate.
   - Source rank i (from 1): the i-th pack in the `packs` list; decide whether the whole pack takes effect by the rules above; units of a pack that takes effect are filtered by include/exclude, and each remaining one is a candidate. When a file in the pack fails to parse or validate, that unit's status is `invalid`, an entry is added to Errors, and the other units proceed normally.
3. Candidates in this profile's `disable` list → `disabled`.
4. **Merge all profiles**: when the same global id appears more than once, keep only the highest-ranked one; the others are `shadowed`. Reason: two profiles referencing the same pack is common and not a conflict.
5. **Apply `replaces`**: go from highest rank to lowest; if unit U is still in the set, remove the units listed in U.replaces from the set, with status `replaced`.
6. The remaining units are `active`, sorted by rank, ties broken by global id in lexical order; this order is the units' **ranking**, used later for topic arbitration and the order of the assembled text.
7. **Merge settings**: starting from the defaults, deep-merge each profile's settings from **lowest to highest** rank (higher ranks are merged later and so override lower ones).

When a profile fails to load (missing directory or profile.yaml, YAML error, plaintext api_key): skip that profile, put the error into `Errors`, and use the other profiles normally. When registry.yaml itself is corrupt, Resolve returns an error.
